Athena

Six agents over one shared state object. It plans the angles, reads the live web, drafts a cited report — then reviews its own draft and rewrites it.

Architecture

The pipeline, and the one arrow that runs backwards

Every stage reads from and writes into one ResearchState object, so the agents communicate through typed state rather than string-passing. Five of the six arrows are the obvious ones. The sixth is the project: the Critic's findings return to the Writer, and the report you read is the second draft.

Context budget

Reading a lot, sending a little

Scraped 662 chunks from 15 pages, ~500 chars each
Retrieved 9 top-3 per sub-question, ranked by cosine similarity
Sent to the writer ~1.5k tokens of evidence, each tagged with its source URL

The naive version of this app hands every scraped chunk to the writer and overflows the context window. Embedding-ranked retrieval is what keeps the prompt small — and small prompts are why the citations stay accurate: the model can only cite what it was shown.

Agents

What each one is responsible for

01planner.py Splits the question into 3 search-optimized sub-questions in JSON mode. Malformed JSON is recovered with a regex; an empty plan falls back to the raw query.
02searcher.py DuckDuckGo, one result per domain so the evidence stays diverse. Social and video hosts are filtered out; a rate limit falls through to known-good URLs rather than returning nothing mid-demo.
03reader.py Fetches with a browser user-agent, then trafilatura with a BeautifulSoup fallback. Content-type and size guards, and every fetch wrapped — one dead link cannot tank a report.
04retriever.py MiniLM embeddings, normalized, into a FAISS inner-product index. Keeps the top 3 chunks per sub-question and carries each one's source URL with it.
05writer.py Writes the report against the retrieved evidence only, with inline [Source N] markers and an auto-generated reference list.
06critic.py Three findings: uncited claims, missing angles, vague hedging. The critique goes back to the writer, which rewrites — streaming — into the final report.

An end-to-end run against the live web with the LLM stubbed, so orchestration, scraping, retrieval and citation assembly are exercised without an API key. Three of fifteen fetches failed — a 403, a read timeout, and a JavaScript-only page — and the report was produced anyway. The Groq calls themselves are still unexercised: they need a key.

One real bug, found by running it. faiss-cpu and torch each bundle their own OpenBLAS. On Windows their thread pools collide and encoding dies mid-batch with a spurious "not enough memory" error — with 5.5 GB free. The retriever caps BLAS threads on win32 before torch loads.

Run it

Local, headless, or deployed

# UI at 127.0.0.1:7860
pip install -r requirements.txt
cp secrets.env.example secrets.env   # paste a free key from console.groq.com
python app.py

# or straight to markdown in reports/
python main.py "What are the latest breakthroughs in Mixture of Experts?"

# full pipeline, stubbed LLM, no key needed
python smoke_test.py

For Hugging Face Spaces: create a Gradio Space, push the folder, and add GROQ_API_KEY as a repository secret. The README already carries the Space frontmatter; the first build takes about five minutes while the embedding weights download.

Next

What eight more hours would buy

  1. Parallelize the searcher and reader with asyncio. Fetching is essentially the whole latency budget and it is entirely I/O-bound — this alone should cut runtime by about 60%.
  2. Add a Source Verifier agent that cross-checks each claim against a second URL and flags anything only one source supports.
  3. Persist runs in a vector DB so Athena remembers past reports and can answer follow-ups without re-searching the same ground.
